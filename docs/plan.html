Implementation Plan

Onyx — Obsidian vault を Web で読むためのアプリケーション

GitHub にバックアップされている SosukeIto/my-vault を唯一のデータソースとし、Better-T-Stack(Bun / Turborepo / Hono / oRPC / TanStack Router)で「Obsidian と同じ読み心地」をブラウザ上に再現する。

作成: 2026-08-23対象 vault コミット: 65df74d(2026-08-22)デモ画面: docs/demo.html

0. 要約

2026-08-24 改訂: 構成を muscle-memo に揃えた第 2〜3 節と第 8 節の「Hono サーバーが git clone して常駐」という設計は廃止。現行は TanStack Start(SSR + server functions)単体の apps/web を Cloudflare Workers にデプロイし、vault の内容は GitHub Actions がビルド時に packages/vault で JSON 化した静的アセット(契約: packages/vault/src/static/types.ts)、認証は better-auth + D1(DB は認証にのみ使用)、PWA、Vite+。取得間隔は my-vault の push 時 + 15 分ごとの定期(変更があるときだけビルド)。手順は README を参照。
242Markdown ノート(Daily 20 / Note 78 / ClaudeLogs 141 / templates 3)
208[[wikilink]] を含むノート数 — リンク解決とバックリンクが中核機能
15 MBリポジトリ総量(PNG 7 / PDF 6 を含む)。丸ごと clone しても軽い
  • データ取得は GitHub API ではなく git clone / pull。サーバーが vault を shallow clone してローカルにインデックスを構築する。API レート制限・ファイル数・日本語パスの問題をまとめて回避できる。
  • Markdown はサーバー側で HTML に変換し、oRPC でメタデータ(frontmatter / 目次 / リンク / バックリンク)と一緒に返す。Obsidian 独自記法(wikilink・embed・callout・highlight・tag)は自作 remark プラグインで扱う。
  • データベースは使わない(2026-08-23 判断)。索引(リンク・バックリンク・タグ・見出し)は同期のたびにメモリ上で再構築する。2.65 MB / 242 ノートなら 1 秒未満で、検索も本文の部分一致走査で数 ms に収まる。
  • UI テキストは原則ゼロ(2026-08-23 ユーザー指示)。読む文字はノート本文だけが理想で、パネル見出し・ボタンラベル・ステータス文言はすべて SVG アイコン + tooltip に置き換える。残すのはファイル名・本文・数字と、設定など代替不能なもののみ。
  • UI は 3 カラム(ツリー / 本文 / アウトライン+バックリンク)。デザインは designer エージェントが作った docs/demo.html を基準にする。iPhone / Android / iPad / MacBook すべてを対象とし、幅に応じて 1〜3 カラムに組み替える(第 12 節)。
  • フェーズ 1〜2 で「ツリー → ノート → リンクを辿る → 検索」が動く MVP、フェーズ 3 で Daily / Claude ログ / グラフ / タグ、フェーズ 4 で同期 Webhook・認証・デプロイ。

2. 技術スタック(Better-T-Stack の選択)

bunx create-better-t-stack@latest . --directory-conflict merge \
  --frontend tanstack-router --backend hono --runtime bun --api orpc \
  --database none --orm none --db-setup none \
  --auth none --payments none --examples none \
  --addons turborepo biome lefthook --web-deploy none --server-deploy none \
  --package-manager bun --install --git --disable-analytics

上記は --dry-run で検証済み(2026-08-23、create-better-t-stack 最新版)。--web-deploy / --server-deploy を省略すると対話プロンプトになるため明示する。

項目選択理由
FrontendTanStack Router(Vite SPA)SSR 不要(閲覧専用・個人用途)。ファイルベースルートと型付き params で /note/$path を安全に扱える。Next より軽く、ビルドも速い
BackendHono + BunBun.spawn で git を実行、起動が速くメモリ索引の再構築に向く。静的ファイル配信(添付画像・PDF)も Hono で完結
APIoRPCTanStack Query との統合が公式。OpenAPI も生成できるので将来 CLI/他ツールから叩ける
DBなし(メモリ索引)正本は git。索引は起動時と同期時にメモリ上で再構築する(packages/vault の純粋な TypeScript)。永続化するものが無いので運用が最も単純。規模が 100 倍になっても数百 MB で収まる
Authなし(Phase 4 で Better-Auth)ローカル運用では不要。公開デプロイ時は bunx create-better-t-stack add で後付けする
Addonsturborepo / biome / lefthookモノレポ並列ビルド、lint+format 一本化、pre-commit で bun run check
Markdownunified(remark / rehype)プラグイン式で Obsidian 記法を足しやすい。gray-matter で frontmatter
UITailwind v4 + shadcn/ui(テンプレ同梱)designer が定義したトークンを CSS 変数として Tailwind に接続する
代替案を退けた理由GitHub Contents API 方式: 未認証 60 req/h、認証済みでも 243 ファイルの全走査が毎回必要で、バックリンク計算に全文が要るため不向き。Cloudflare Workers: git を実行できず永続ディスクもないため、本プランでは Docker + VPS を前提にする(Workers 化する場合は API 方式 + KV キャッシュに切り替える)。

3. アーキテクチャ

GitHub: my-vault

  • obsidian-git が 20 分ごとに push
  • Phase 4: push Webhook → /api/sync

apps/server(Hono / Bun)

  • sync: git clone --depth 1 → 5 分ごと git pull
  • indexer(packages/vault): 全 .md を走査 → frontmatter / リンク / タグ / 見出しをメモリ上の索引に構築(同期ごとに丸ごと再構築)
  • renderer: unified で HTML 化(キャッシュ: path + commit)
  • oRPC: vault / note / search / daily / graph
  • /files/*: 添付画像・PDF 配信
data/vault(clone)のみ。DB は持たない

apps/web(TanStack Router)

  • 3 カラム shell(ツリー / 本文 / アウトライン+バックリンク)
  • oRPC + TanStack Query でデータ取得・キャッシュ
  • 本文 HTML 内の a[data-wikilink] クリックを Router 遷移に差し替え
  • テーマ(light/dark)、コマンドパレット検索(⌘K)
designer が作るトークン・アイコン・レイアウトを使用

メモリ索引のデータモデル(TypeScript)

VaultIndex {
  commit: string; builtAt: Date;
  notes: Map<path, Note>            // title · folder · frontmatter · body · headings[] · tags[] · modified
  byBasename: Map<basename, path[]>  // wikilink 解決用
  links: Link[]                       // from · to(null = 未作成) · target(原文) · alias · heading · kind(wiki|embed|md)
  backlinks: Map<path, Link[]>       // links から導出
  tags: Map<tag, path[]>
  searchText: Map<path, string>      // NFKC 正規化 + 小文字化した title+body(検索用)
}

索引は不変オブジェクトとして作り、同期で commit が変わったときだけ丸ごと作り直して差し替える(差分更新はしない。2.65 MB なら全走査のほうが単純で速い)。検索は searchText の部分一致走査(日本語は形態素解析なしで部分一致が自然)で、ヒット周辺をスニペットとして切り出す。将来ノートが数千件を超えたら bigram 転置索引を packages/vault 内に足すだけでよい。

5. Markdown パイプライン

gray-matter            frontmatter を分離(title/date/tags/…)
 └ preprocess          タブ区切りインデント行の正規化、%%コメント%% の除去
remark-parse → remark-gfm → remark-math → remark-frontmatter
 └ remark-obsidian     自作: [[link|alias#heading]] / ![[embed]] / ==mark== / #tag / > [!callout]
remark-rehype → rehype-slug → rehype-katex → rehype-shiki(コード) → rehype-sanitize → rehype-stringify
 └ 出力: { html, toc[], links[], tags[] }   ※ html は <article data-cssclasses="vocab"> に包む

リンク解決ルール(Obsidian 互換)

  1. [[Daily Note]] → basename 完全一致を全 vault から検索。1 件ならそれ、複数なら参照元に最も近いパス(Obsidian の shortest-path 挙動)
  2. [[01_Note/03_考え方/アウトラインから書く]] → vault ルート相対パスとして解決
  3. [[note#見出し]] → rehype-slug と同じスラグ規則でアンカーを付ける
  4. 解決不能 → <a class="wikilink unresolved">(薄色・クリックで「未作成ノート」ページへ)
  5. 添付ファイル ![[Pasted image 20260101120000.png]] → 同階層 attachments/ → 全 vault の basename 検索の順。URL は /files/<encoded path>
Daily Note の独自階層00_Daily/2026/08/20.md のように「行頭タブでぶら下げた非リスト行」が多用されている。CommonMark ではタブ 1 つでコードブロック扱いになるため、前処理で「連続する非リスト行のタブインデント」をネストしたリストに変換する(Obsidian の見え方に合わせる)。これは MVP のテスト対象に含める。

10. リスクと判断

私的情報の露出

私的なメモや添付ファイルが含まれる。リポジトリ自体は公開だが、Web アプリを公開する前に認証(Phase 4)を必須にし、それまではローカル(localhost)のみで運用する。

日本語・空白・全角記号を含むパス

会社案内　資料.pdf(全角スペース)のような名前がある。URL はセグメント単位で encodeURIComponent、サーバーは path.normalize 後に vault ルート外を拒否する。

リンク解決の曖昧さ

同名 basename が複数ある場合の挙動は Obsidian 準拠(最短パス)にし、テストで固定する。解決結果は links.toPath に保存し、UI はそれを信じる。

Daily Note の非標準インデント

タブぶら下げ行がコードブロック化する問題。前処理で対処するが、完全一致は狙わず「読める」ことを基準にする。

メモリ索引のスケール

本文をメモリに持つため、ノート数が数万件・数百 MB 規模になると再構築時間とメモリが効いてくる。その時点で bigram 転置索引の追加か、SQLite(FTS5)の導入を再検討する。現状(2.65 MB)では問題にならない。

同期の競合

obsidian-git は merge 方式で push するため履歴が直線でないことがある。Web 側は git fetch && git reset --hard origin/main で常にリモートを正とする(ローカル変更を持たない)。

実装ルール(designer + ワーカー C)

  • レイアウトは grid-template-columns: auto minmax(0, 1fr) auto を基本にし、本文カラムに min-width: 0 を必ず付ける(横はみ出しの主因)。pre / table / 長い URL は自分のコンテナ内でスクロール(overflow-x: auto、overflow-wrap: anywhere)
  • 高さは 100dvh、ヘッダー・タブバーの padding に env(safe-area-inset-*)(iPhone のノッチ/ホームバー対応)
  • タップ領域 44×44px 以上、ホバー依存の UI を作らない(ツリーの開閉・リンクプレビューはタップでも開ける)。@media (hover: hover) でホバー効果をデスクトップ限定にする
  • フォントサイズは本文 16px(phone)/ 17px(tablet 以上)。<meta name="viewport"> で拡大縮小は禁止しない(アクセシビリティ)
  • 本文 HTML はサーバーから返るため、画像は max-width: 100%; height: auto、loading="lazy" を rehype 側で付与する
  • 検証は 390 / 820 / 1180 / 1440 の 4 幅でヘッドレス Chrome のスクリーンショットを撮って確認する(受け入れ条件に含める)
  • UI テキスト最小化: 見出し・ラベル・プレースホルダ・ステータスは文字を持たず、アイコン + aria-label + tooltip で表現する。frontmatter のキー名もアイコン化し、キー名は tooltip に退避。アイコン語彙は designer が components/icons/README.md に一覧化し、同じ概念に同じアイコンを使う

  • 加えて Obsidian と同じ「← →」ボタンをヘッダーに置き、router.history.back() / forward() を呼ぶ。履歴の先頭・末尾では disabled にする(履歴長は history.length と自前スタックで追跡)
